# 平台隧道传输诊断与连接恢复

## 故障证据与目标

2026-10-22 真机远程更新的 SSH、sudo 和空间预检通过，上传计数到 2 MiB 后，平台报告转发队列阻塞 30 秒超时；随后设备控制连接超时，重试一直停留在握手阶段。上传计数表示进入 SSH 发送流水线的字节，不等于设备落盘量。此次未进入安装。

本次目标是明确数据停止前进的位置，并保证控制连接失败后使用新的传输连接重新握手。共享 gRPC 连接是否为上传故障根因仍需诊断数据确认，本次不调整窗口、队列容量、超时和协议，不修改设备接入配置或上位机阶段归类。

## 输入、输出与异常处理

- 输入仍为已有设备控制消息和隧道帧，每帧最多 64 KiB，目标仍限本机环回和白名单服务。
- 设备隧道结束时输出设备、服务、隧道 ID、平台实际接收字节、本机 TCP 实际写入字节、本机 TCP 实际读取字节、成功交给 gRPC 的字节、最后进展时间及关闭原因。部分写入也纳入实际字节统计。
- 平台在转发超时时区分上下行，输出累计成功入队字节、当前帧字节、等待时间及队列状态；成功入队不表示对端收到。控制连接独立统计握手、心跳和重连原因。
- 日志不记录令牌、票据、密码、SSH 内容或文件内容。方向与字节摘要遵循已有隧道日志隐私边界。
- 设备收到控制失效时，仍先取消并回收旧隧道及所有工作线程，再开始下一次握手。每次接入尝试使用新的 channel 和独立子连接池，防止重新创建对象后仍复用旧底层连接；不重放旧业务数据。
- 单隧道失败只结束对应隧道；控制连接失效才取消该连接的所有隧道。上位机接口、认证和更新任务契约保持兼容。

gRPC 的独立子连接池参数语义参见 [官方通道参数说明](https://grpc.github.io/grpc/cpp/group__grpc__arg__keys.html)，本次使用 `GRPC_ARG_USE_LOCAL_SUBCHANNEL_POOL`，不修改生产超时值。

## 测试与验收

先补测试，再实现恢复和诊断：

1. 假平台主动结束第一次控制 RPC，第二次接入必须使用不同的 TCP 对端地址，验证真正重新建立传输连接。
2. 真实本机 TCP 后端与 C++ gRPC 假平台传输 50 MiB 二进制数据，校验完整内容和半关闭尾部，传输过程中等待并收到新的控制心跳。
3. 平台测试覆盖单向背压下反向和心跳仍可处理、取消后隧道清理及重新打开。两端测试均不替代真实 SSH 和现场网络验证。

用户要求修改后提交推送，由 GitLab 编译。本机缺少下位机 Linux/gRPC 构建环境，因此 C++ 测试先落盘但无法在本机执行红绿验证；不安装构建环境、不使用远端容器、不部署或重启真机。执行可用协议检查、配置行为检查和差异检查，编译及 C++ GTest 结果以本次提交的 GitLab 作业为准。

本地已通过 `python script/dev/check_platform_agent_config.py` 的真实 C++ 配置和目标解析检查、`python script/dev/test_platform_agent_contract.py` 的一项协议检查，以及本次修改文件的 `clang-format --dry-run --Werror`、`git diff --check`。这些检查不包含 gRPC 隧道集成测试；新增的两个 GTest 由 GitLab 编译执行。

## 后续现场验证

GitLab 通过后，设备与平台部署需另行确认。使用约 50 MB 安装包核对各端计数与摘要，验证 SSH 上传、控制心跳、断线重连及再次上传；若仍阻塞，根据新日志选择故障端修复。只有证据确认连接级影响时，才进一步讨论控制流与数据流的底层连接隔离。
