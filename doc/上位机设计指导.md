# 上位机设计指导

## 1. 文档目的

本文档用于总结当前 `mskdsp` 软件的上位机设计思路，指导后续的产品原型、前端页面、接口联调与运维操作设计。

本文档基于当前仓库中的模块职责、`protobuf` 接口定义与模块文档整理而成，重点回答以下问题：

- 上位机应该如何理解本系统的架构分层。
- 上位机应该如何划分菜单与页面。
- 上位机应当采用怎样的操作流程。
- 上位机在交互设计上需要避免哪些常见误区。

## 2. 系统定位与架构理解

当前系统不适合按“单一设备监控软件”来设计，更适合设计为“配置编排台 + 运行运维台”。

从上位机视角看，系统主要分为三层：

- `ModuleManager`：负责模块发现、模块启动停止、运行地址查询，是上位机的统一入口。
- `DataCenter`：负责连接注册、标签注册、点值路由、实时值快照与订阅，是系统的数据总线。
- 业务模块：包括 `IEC104`、`ModbusRTU`、`DLT645`、`AGC`、`MQTTManager` 等，分别负责协议接入、控制策略或联调能力。

其中：

- `IEC104`、`ModbusRTU`、`DLT645` 负责协议连接与点表。
- `AGC` 负责控制组建模、成员分配与控制输出。
- `MQTTManager` 更偏向底层通道与联调能力，不建议作为普通运维用户的主入口。
- `ConfigPusher` 更适合作为初始化配置编排工具，不适合作为上位机日常在线配置的统一入口。

## 3. 上位机设计总原则

- 按“用户任务”划分页面，不按模块源码目录机械拆分页面。
- 正常主流程只要求“启动模块”；链路或控制组功能由模块在配置达到可运行条件后自动启动。
- 明确区分“协议点表”和 `DataCenter` 的 `ConnTags`。
- 明确显示 `conn_id`，不要把它隐藏成内部字段。
- 配置流程应遵循“先启动模块、再建连接或控制组、再下发点表或控制配置、再配路由、最后确认对象自动进入运行态”的顺序。
- `UPPER` 模式下，只要模块配置目录存在持久化配置文件痕迹，`ModuleManager` 就会自动启动对应模块；模块再自行判断 pb 是否可恢复、对象是否可自动启动模块内功能。
- 配置错误、pb 恢复失败、点表或对象不匹配时，模块服务应保持在线，并通过 `last_error` 与日志等待上位机补救。
- 配置页面与运行页面分离，避免运维时误改配置。
- 协议页尽量复用统一页面骨架，减少不同协议页面的学习成本。
- 联调工具与日常运维页面分离，避免普通用户误用底层调试能力。

## 4. 一级导航建议

建议将上位机划分为以下一级导航：

1. `总览`
2. `模块运维`
3. `规约接入`
4. `数据总线`
5. `控制策略`
6. `告警与日志`
7. `联调工具`

其中：

- `总览` 面向值班与巡检。
- `模块运维` 面向模块级启停与运行状态确认。
- `规约接入` 面向协议连接、点表与运行控制。
- `数据总线` 面向跨模块连接关系、标签与路由。
- `控制策略` 面向 AGC 等控制逻辑配置。
- `告警与日志` 面向问题排查。
- `联调工具` 面向开发、调试和现场联机人员。

## 5. 各页面设计建议

## 5.1 总览

总览页建议展示以下信息：

- 当前已发现模块数。
- 当前运行中的模块数。
- 当前运行中的协议连接数。
- 当前运行中的 AGC 控制组数。
- `DataCenter` 已配置连接数与路由数。
- 当前活跃告警数。
- 最近错误摘要。
- 关键模块在线状态。
- 最近一段时间的报文量或点值更新量。

总览页不建议承载复杂配置，只做状态汇总与快捷跳转。

## 5.2 模块运维

模块运维页应以 `ModuleManager` 为核心，展示：

- 模块名。
- 版本号。
- 依赖关系。
- 是否运行。
- `outer_grpc_server` 地址。
- 最近错误信息。
- 启动模块、停止模块、刷新运行地址等操作。

本页的目标是让用户先确认模块服务层是否正常，再进入具体业务页。

## 5.3 规约接入

`规约接入` 下建议拆分三个二级页面：

- `IEC104`
- `ModbusRTU`
- `DLT645`

三类协议页面建议采用一致的结构：

1. 连接列表区
2. 连接配置区
3. 点表配置区
4. 运行状态区
5. 运行操作区
6. 报文日志区

这样做的好处是：

- 用户对不同协议页的认知一致。
- 新增协议时也更容易沿用相同交互框架。
- 前端实现可复用通用组件。

### IEC104 页面建议

应重点展示：

- `role` 与 `station_role`
- 本地地址与远端地址
- `ca`、`oa`
- `apci` 参数
- 对时触发 tag
- 点表 `tag <-> IOA`
- 自发上送参数
- 对时按钮
- 当前状态与最后错误

### ModbusRTU 页面建议

应重点展示：

- 传输类型 `TRANSPORT_SERIAL` 或 `TRANSPORT_MQTT_UART`
- 本地串口参数或远端 `serial_port`
- `device_id`
- `poll_interval_ms`
- `read_plan`
- 顶层 MQTT 参数
- 点表 `tag <-> function/address`
- 当前状态与最后错误

当用户选择 `TRANSPORT_MQTT_UART` 时，界面应联动展示 MQTT 配置区与 `serial_port` 配置区，避免漏填。

还应注意以下专项约束：

- 点位功能码为 `0x06` 时，仅允许单个 16 位寄存器写入。
- 点位功能码为 `0x10` 时，可用于 16 位或 32 位寄存器写入。
- 建议将“采集点 tag”和“控制点 tag”分开配置，控制命令通过 `DataCenter` 路由写入 ModbusRTU 控制点。

### DLT645 页面建议

应重点展示：

- `protocol_variant`
- `meter_addr`
- `device_no`
- `comm_mode`
- `poll_interval_ms`
- `poll_item_interval_ms`
- MQTT 参数
- 点表 `tag <-> di`
- 块读配置 `block_di`
- 当前状态与最后错误

对于 `DLT645PCD`，建议提供“公共模板 + device_nos 批量展开预览”能力，避免用户为多个设备重复维护相同配置。

还应注意以下专项约束：

- 串口模式下建议显式展示 `serial_port` 与串口参数。
- 若页面提供采集节奏编辑，需区分 `poll_interval_ms`（整轮扫描后等待）与 `poll_item_interval_ms`（单次收发之间等待）。
- 运行态建议按 `meter_addr` 聚合展示，并保留每个 `device_no` 的逻辑连接状态。
- 如需将串口异常状态展示给运维，建议对 `Frametimeout`、`Porterror`、`Buffull`、`Formaterror` 提供中文映射说明。

### 协议专项补充建议

对于厂商协议页、寄存器工具页或参数写入页，建议统一遵循以下规则：

- 将“设置参数类”和“实时参数类”分开展示，避免地址重叠导致误用。
- 录入寄存器地址时，同时展示十进制和十六进制。

## 5.4 数据总线

`数据总线` 页面应单独存在，不应并入协议页。

建议拆分为四个区域：

- 连接注册表
- 标签注册表
- 路由管理
- 实时值监视

连接注册表建议展示：

- `module_name`
- `conn_name`
- `conn_id`

标签注册表建议展示：

- 连接对应的 tags
- tag 数量
- 是否已同步

路由管理建议同时提供：

- 表格视图
- 源到目标的关系图视图

实时值监视建议支持：

- 单连接最新值快照
- 按 tag 过滤
- 订阅实时更新

需要特别说明的是：

- `ConnTags` 不是协议点表。
- `Route` 是 `src(conn_id, tag) -> dst(conn_id, tag)` 的有向绑定。
- `DataCenter` 当前只提供最新值与实时订阅，不是历史库。

## 5.5 控制策略

当前主要承载 `AGC`。

建议页面结构为：

- 控制组列表
- 控制组配置
- 成员配置
- 输入输出点说明
- 运行状态
- 控制日志

应重点展示：

- `group_name`
- `conn_id`
- `p_cmd`
- 成员量测点与设定点
- 分配策略
- 派生输出点
- 当前状态与最后错误

需要注意：

- 当前 AGC 不应继续展示旧版 `loop`、`kp`、`deadband_kw`、`max_step_kw` 等参数。
- 页面文案应强调“相关输入变化时直接按目标总功率分配”。

## 5.6 告警与日志

建议统一建设独立的日志与告警页面，而不是分散在各功能页。

建议支持以下维度检索：

- 模块名
- 连接名
- 控制组名
- `conn_id`
- `meter_addr`
- `device_no`
- `tag`
- 时间范围

建议重点支持以下内容：

- 模块启动失败
- 连接启动失败
- `PENDING_DELETE`
- 路由配置错误
- MQTT 连接失败
- 串口超时
- IEC104 链路断开
- AGC 分配受限
- 报文收发日志

协议页只展示摘要和最近日志，完整排障入口应统一进入本页。

## 5.7 联调工具

联调工具应与日常运维页面分开。

建议提供以下能力：

- `DataCenter` 实时订阅
- `DataCenter` 最新值快照
- MQTT 请求应答调试
- MQTT 订阅调试
- IEC104 手工对时

调试界面建议直接展示以下字段：

- 发送方向
- 接收方向
- 完整十六进制报文
- 功能码
- 寄存器起始地址
- 数量或写入值

此页适合开发、调试与现场联机人员使用，不建议向普通运维人员暴露过多底层能力。

## 6. 推荐操作流程

## 6.1 首次建站或新增系统接入

推荐流程如下：

1. 先规划稳定的 `module_name + conn_name/group_name` 命名。
2. 在 `模块运维` 中启动 `DataCenter` 与目标模块。
3. 通过运行信息获取各模块 `outer_grpc_server`。
4. 在对应业务页中创建连接或控制组，拿到稳定的 `conn_id`。
5. 在协议页下发点表。
6. 在 `数据总线` 中配置 `ConnTags` 与 `Routes`。
7. 返回业务页，确认链路或控制组已依据当前配置自动进入运行态；若未进入运行态，则结合 `state`、`last_error` 与日志修正配置后重新下发。
8. 进入实时值与报文日志页完成联调确认。

## 6.2 新增协议连接

推荐顺序如下：

1. 启动模块。
2. 新建连接。
3. 下发点表。
4. 配置路由。
5. 观察对象是否自动进入运行态；若未进入运行态，则修正配置后重新下发。
6. 观察最新值、状态与日志。

不建议先启动连接再补点表或路由，否则容易出现“模块运行了但业务不通”的误判。

## 6.3 新增 AGC 控制组

推荐顺序如下：

1. 启动 `DataCenter` 与 `AGC` 模块。
2. 创建控制组并获取 `conn_id`。
3. 配置 `p_cmd`、成员量测点、成员设定点与派生输出点。
4. 在 `数据总线` 配置上游输入路由与下游输出路由。
5. 观察控制组是否自动进入运行态；若未进入运行态，则结合 `last_error` 与日志修正配置后重新下发。
6. 观察 `p_total_meas`、`p_total_target`、成员设定输出与日志。

## 6.4 日常运行

日常运行建议以以下页面为主：

- `总览`
- `告警与日志`
- `数据总线` 的实时值监视
- 各业务页的运行状态摘要

原则上，运行期用户应尽量少进入配置编辑页面，减少误操作风险。

## 6.5 故障处置

建议按层次定位问题：

### 模块层

若模块不可达或接口连接失败：

- 返回 `模块运维`
- 刷新 `GetRunningModuleInfo`
- 确认地址是否变化
- 必要时重新启动模块

### 连接层

若连接未进入运行态：

- 查看 `state`
- 查看 `last_error`
- 若对象仍在运行态且需要修改配置，先停止对象功能
- 修正连接参数、点表或 MQTT 等前置配置
- 重新下发配置，等待模块自动再次尝试启动连接功能

### 数据层

若模块已运行但数据不通：

- 检查 `conn_id` 是否匹配
- 检查 `ConnTags` 是否存在且正确
- 检查 `Route` 是否配置完整
- 检查源 tag 与目标 tag 是否一致或按预期重写

### 删除失败

若对象删除后进入 `PENDING_DELETE`：

- 先确认 `DataCenter` 是否可达
- 恢复后重试删除
- 必要时重新建立对象并重新梳理路由

## 7. 关键交互约束

上位机在设计时必须强调以下约束：

- “启动模块”应作为正常主路径的唯一启动动作。
- 不应把“启动连接功能/启动控制组功能”设计成正常主路径按钮；如因兼容保留，也应明确标注为诊断或补救入口。
- `conn_id` 应展示为关键只读字段。
- 协议点表编辑页与 `DataCenter` 标签注册页必须分开。
- 修改运行中对象前，应先停止连接功能或控制组功能。
- 对删除操作应给出二次确认，尤其是涉及 `DeleteConnection`、`DeleteLink`、`DeleteGroup` 时。
- 对 `replace=true` 类操作应做显式提醒，避免用户误覆盖既有配置。

## 8. 两种接入模式建议

## 8.1 上位机直控模式

适用于在线维护、单点调试、增量调整。

推荐顺序：

1. 启动模块
2. 创建连接或控制组
3. 下发点表或控制配置
4. 配置 `DataCenter` 路由
5. 确认对象依据当前配置自动进入运行态；未进入运行态时查看 `state`、`last_error` 与日志并修正配置

## 8.2 ConfigPusher 初始化模式

适用于批量初始化、预制配置下发、现场快速部署。

需要注意：

- `ConfigPusher` 当前更偏向配置编排执行器。
- 它不适合作为上位机统一的日常在线操作入口。
- 上位机在该模式下更适合作为配置生成、校验、导入与状态观察工具。

## 9. 后续扩展建议

如果后续继续完善上位机，建议优先补齐以下能力：

- 原型级页面草图
- 页面到 gRPC 调用的映射表
- 角色权限划分
- 历史数据或趋势系统对接方案
- 常见告警到中文处理建议的映射表
- 配置导入导出模板
