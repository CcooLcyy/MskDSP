# 上位机设计指导

## 1. 文档目的

本文档用于总结当前 `mskdsp` 软件的上位机设计思路，指导后续的产品原型、前端页面、接口联调与运维操作设计。

本文档基于当前仓库中的模块职责、`protobuf` 接口定义与模块文档整理而成，重点回答以下问题：

- 上位机应该如何理解本系统的架构分层。
- 上位机应该如何划分菜单与页面。
- 上位机应当采用怎样的操作流程。
- 上位机在交互设计上需要避免哪些常见误区。

## 2. 系统定位与架构理解

当前系统不适合按“单一设备监控软件”来设计，更适合设计为“配置编排台 + 运行运维台”。

从上位机视角看，系统主要分为三层：

- `ModuleManager`：负责模块发现、模块启动停止、运行地址查询，是上位机的统一入口。
- `DataCenter`：负责连接注册、标签注册、点值路由、实时值快照与订阅，是系统的数据总线。
- 业务模块：包括 `IEC104`、`ModbusRTU`、`DLT645`、`AGC`、`AVC`、`Calc`、`MQTTManager`、`DigitalInput` 等，分别负责协议接入、控制策略、遥信采集或联调能力。

其中：

- `IEC104`、`ModbusRTU`、`DLT645` 负责协议连接与点表。
- `AGC` 负责控制组建模、成员分配与控制输出。
- `Calc` 负责计算分组建模、类型化运算与结果点发布。
- `MQTTManager` 更偏向底层通道与联调能力，不建议作为普通运维用户的主入口。
- `DigitalInput` 负责板载 4 路 DI 遥信采集；上位机无需增加专用配置页，直接在 `数据总线` 页面选择 `DigitalInput/board-di` 的 `DI1` 至 `DI4` 建立路由即可。
- `ConfigPusher` 更适合作为初始化配置编排工具，不适合作为上位机日常在线配置的统一入口。

## 3. 上位机设计总原则

- 按“用户任务”划分页面，不按模块源码目录机械拆分页面。
- 正常主流程应区分“启动模块”和“启动模块内功能”：先启动模块，再按需要显式启动模块内的链路连接功能。
- 明确区分“协议点表”和 `DataCenter` 的 `ConnTags`。
- 对于 `IEC104`、`ModbusRTU`、`DLT645`、`AGC`、`Calc` 等会自动同步 `ConnTags` 的模块，上位机不应把 `ConnTags` 设计成第二份需要重复维护的主配置；正常主路径应先在业务页配置点表、控制组或计算分组，再到 `数据总线` 页面直接基于已同步出来的 tags 配置路由。
- 明确显示 `conn_id`，不要把它隐藏成内部字段。
- 配置流程应遵循“先启动模块、再建连接或控制组、再下发点表或控制配置、再配路由、最后按需要显式启动模块内的链路连接功能并确认对象进入运行态”的顺序。
- `UPPER` 模式下，只要 `./conf/config.db` 中存在对应模块的 SQLite 持久化配置痕迹，`ModuleManager` 就会自动启动对应模块；模块再自行判断 SQLite payload 是否可恢复，以及恢复出的对象是否需要自动恢复模块内功能。
- 配置错误、SQLite payload 恢复失败、点表或对象不匹配时，模块服务应保持在线，并通过 `last_error` 与日志等待上位机补救。
- 配置页面与运行页面分离，避免运维时误改配置。
- 协议页尽量复用统一页面骨架，减少不同协议页面的学习成本。
- 上位机应尽量覆盖 `jsonc` 中有业务意义的可配项，但应按页面语义自然归组，不必为每个字段单独设计配置入口。

## 4. 一级导航建议

建议将上位机划分为以下一级导航：

1. `总览`
2. `模块运维`
3. `规约接入`
4. `数据总线`
5. `控制策略`

其中：

- `总览` 面向值班与巡检。
- `模块运维` 面向模块级启停与运行状态确认。
- `规约接入` 面向协议连接、点表与运行控制。
- `数据总线` 面向跨模块连接关系、标签与路由。
- `控制策略` 面向 AGC、AVC、Calc 等控制/计算逻辑配置。

## 5. 各页面设计建议

## 5.1 总览

总览页建议展示以下信息：

- 当前已发现模块数。
- 当前运行中的模块数。
- 当前运行中的协议连接数。
- 当前运行中的 AGC/Calc 分组数。
- `DataCenter` 已配置连接数与路由数。
- 最近错误摘要。
- 关键模块在线状态。
- 最近一段时间的报文量或点值更新量。

总览页不建议承载复杂配置，只做状态汇总与快捷跳转。

## 5.2 模块运维

模块运维页应以 `ModuleManager` 为核心，展示：

- 模块名。
- 版本号。
- 依赖关系。
- 是否运行。
- 扫描可用性。
- 启动模块、停止模块、刷新运行状态等操作。

本页的目标是让用户先确认模块服务层是否正常，再进入具体业务页。

若上位机内部需要直连模块接口，应根据 `GetRunningModuleInfo` 自动刷新连接信息，但不要求用户手工识别或维护地址。

模块最近错误摘要更适合来自统一的日志或告警聚合，而不是直接依赖 `ModuleManager` 运行信息返回。

## 5.3 规约接入

`规约接入` 下建议拆分三个二级页面：

- `IEC104`
- `ModbusRTU`
- `DLT645`

三类协议页面建议采用一致的结构：

1. 连接列表区
2. 连接配置区
3. 点表配置区
4. 运行状态区
5. 运行操作区

这样做的好处是：

- 用户对不同协议页的认知一致。
- 新增协议时也更容易沿用相同交互框架。
- 前端实现可复用通用组件。

协议报文观测能力本期不作为页面固定结构的一部分；后续如需建设，建议优先采用统一的报文日志 RPC 或统一观测组件，而不是继续依赖各模块分散输出运行日志。

### IEC104 页面建议

应重点展示：

- `role` 与 `station_role`
- 本地地址与远端地址
- `ca`、`oa`
- `apci` 参数
- 点表 `tag <-> IOA`
- 自发上送参数
- 对时按钮
- 当前状态与最后错误

需要特别说明的是：

- IEC104 对时触发使用模块内置保留 tag。
- 上位机不提供该 tag 的配置入口。
- 如需触发对时，可通过手动对时入口或既定路由方式触发。

### ModbusRTU 页面建议

应重点展示：

- 传输类型 `TRANSPORT_SERIAL` 或 `TRANSPORT_MQTT_UART`
- 本地串口参数或远端 `serial_port`
- `device_id`
- `poll_interval_ms`
- `read_plan`
- 模块级共享 MQTT 配置
- 点表 `tag <-> function/address`
- 当前状态与最后错误

当用户选择 `TRANSPORT_MQTT_UART` 时，界面应联动展示并校验模块级共享 MQTT 配置区与 `serial_port` 配置区，避免漏填。

需要特别说明的是：

- MQTT 配置属于 ModbusRTU 模块级共享配置，不是每条链路单独维护一份。
- 页面可放在 ModbusRTU 协议页内统一管理，但不建议拆成链路级字段。

还应注意以下专项约束：

- 点位功能码为 `0x06` 时，仅允许单个 16 位寄存器写入。
- 点位功能码为 `0x10` 时，可用于 16 位或 32 位寄存器写入。
- 建议将“采集点 tag”和“控制点 tag”分开配置，控制命令通过 `DataCenter` 路由写入 ModbusRTU 控制点。

### DLT645 页面建议

应重点展示：

- `conn_name`
- `conn_id`
- `protocol_variant`
- `meter_addr`
- `device_no`
- `comm_mode`
- `poll_interval_ms`
- `poll_item_interval_ms`
- 模块级共享 MQTT 配置
- 点表 `tag <-> di`
- 块读配置 `block_di`
- 当前状态与最后错误

对于 `DLT645PCD`，建议提供“公共模板 + device_nos 批量展开预览”能力，避免用户为多个设备重复维护相同配置。

还应注意以下专项约束：

- MQTT 配置属于 DLT645 模块级共享配置，对当前模块内相关链路复用。
- 串口模式下建议显式展示 `serial_port` 与串口参数。
- 若页面提供采集节奏编辑，需区分 `poll_interval_ms`（整轮扫描后等待）与 `poll_item_interval_ms`（单次收发之间等待）。
- 运行态建议按 `meter_addr` 聚合展示，并保留每个 `device_no` 的逻辑连接状态。
- 对 LoRa 档案批量联调场景，验收应按“单条 `addslaveNode` 消息 + `body` 数组多元素”检查，不要按“每档案一条 MQTT 消息”设计联调脚本。
- 如需将串口异常状态展示给运维，建议对 `Frametimeout`、`Porterror`、`Buffull`、`Formaterror` 提供中文映射说明。

建议同时遵循以下运行态展示与交互约束：

- `UpdateConfig`、`UpsertLink`、`UpsertPointTable` 返回成功，只表示本次配置请求已被模块接受并完成必要落盘，不等价于链路已经进入 `RUNNING`。
- 当前版本没有单独的“后台重试中”字段；上位机应结合 `LinkInfo.state` 与 `LinkInfo.last_error` 判断链路是否仍处于自动恢复或档案重试阶段。
- 建议将 `STOPPED + last_error 为空` 视为普通未启动状态；将 `STOPPED + last_error 非空` 视为需要重点关注的状态。若 `last_error` 以 `档案添加失败:` 开头，可展示“等待模块后台重试”之类提示。
- 若模块返回的 `last_error` 为 `档案添加失败: 帧超时`、`档案添加失败: 端口错误` 等中文文案，页面应原样展示，不建议再次抽象成统一的“启动失败”。
- 对 `COMM_MODE_LORA` 与 `COMM_MODE_CARRIER` 下的 `addslaveNode` / `delslaveNode`，建议按以下语义展示对下 `status`：`0/ok/success` 为成功，`1/fail` 为失败，`2/frametimeout` 为帧超时，`3/porterror` 为端口错误，`4/buffull` 为缓冲区满，`5/formaterror` 为格式错误；响应缺少 `status` 或 `status` 类型异常时按失败展示。
- 对普通抄表/写入请求，`status=2` 仍按“帧超时”理解；但对 Lora/载波 `addslaveNode` 响应，数值型 `status=2`（含字符串 `"2"`）需要按“档案已存在”展示，并视为档案添加已完成；字符串 `Frametimeout` 仍按“帧超时”展示。
- 当同地址首个连接进入运行态前需要执行 `addslaveNode` 且首次失败时，模块会保持链路在 `STOPPED` 并将最近失败原因写入 `last_error`；模块随后会在后台每 5 秒重试一次 `addslaveNode`，直到成功、上位机调用 `StopLink` 停止连接功能，或上位机重新下发链路/点表配置。
- 若首轮 `addslaveNode` 返回数值型 `status=2`（含字符串 `"2"`），表示档案已存在；模块不会进入后台重试，而是直接继续后续抄表流程。即使没有发生后台重试，当上位机后续调用 `StopLink` 停止连接功能并使该地址生命周期结束时，模块仍会按生命周期发送 `delslaveNode` 删除档案。
- 后台重试成功后，模块会自动继续启动连接功能并将链路切换为 `RUNNING`，无需上位机再次补发 `StartLink`。`UpdateConfig` 更新 MQTT 参数后，也不会单独中断已存在的档案后台重试；新的 MQTT 参数会直接作用于后续重试请求。
- 若上位机直接调用 `StartLink` 且本次首发 `addslaveNode` 失败，`StartLink` 会立即返回失败；但模块后台仍会继续重试档案添加。页面不应把这次 RPC 失败简单理解为“后续不会再尝试”。
- `UpdateConfig`、`UpsertLink`、`UpsertPointTable` 不会触发自动启动；配置类 RPC 成功后，链路保持 `STOPPED` 属于正常结果。若业务需要启动模块内的链路连接功能，应由上位机显式调用 `StartLink`，并在调用后继续轮询 `GetLink` 或 `ListLinks`，直到链路进入 `RUNNING` 或人工停止。
- 建议在页面提供“停止连接功能”入口；该操作除停止运行中的链路外，也用于终止当前档案后台重试。若页面允许改配，建议在重新下发链路或点表前提示用户：当前后台重试会先被终止，再按新配置重新判定是否启动。
- 若 `last_error` 长时间保持 `档案添加失败: 帧超时/端口错误/缓冲区满/格式错误/失败`，应同时检查 MQTT 头端与对应响应主题、Lora/载波头端在线状态、现场设备地址与档案能力；建议在操作日志或页面事件流中展示“首轮档案添加失败后已进入后台重试”这一事实。

### 协议专项补充建议

对于厂商协议页、寄存器工具页或参数写入页，建议统一遵循以下规则：

- 将“设置参数类”和“实时参数类”分开展示，避免地址重叠导致误用。
- 录入寄存器地址时，同时展示十进制和十六进制。

## 5.4 数据总线

`数据总线` 页面应单独存在，不应并入协议页。

建议拆分为四个区域：

- 连接注册表
- 标签注册表
- 路由管理
- 实时值监视

连接注册表建议展示：

- `module_name`
- `conn_name`
- `conn_id`

标签注册表建议展示：

- 连接对应的 tags
- tag 数量
- 是否已同步

其中建议区分两类来源：

- 协议模块或控制模块自动同步的 tags：默认只读展示，用于路由配置、校验与诊断。
- 需要人工维护的其他连接标签注册表：才提供编辑入口。

路由管理建议同时提供：

- 表格视图
- 源到目标的关系图视图

实时值监视建议支持：

- 单连接最新值快照
- 按 tag 过滤
- 订阅实时更新

需要特别说明的是：

- `ConnTags` 不是协议点表。
- 对于 `IEC104`、`ModbusRTU`、`DLT645`、`AGC`、`Calc` 等已实现自动同步 `ConnTags` 的模块，`数据总线` 页面更适合直接展示已存在的连接与 tags，并让用户完成 `Route` 绑定，而不应要求用户重复手工录入第二份点表。
- `Route` 是 `src(module_name, conn_name, tag) -> dst(module_name, conn_name, tag)` 的有向绑定；`conn_id` 只作为当前运行态展示、过滤和旧配置兼容字段。
- `DataCenter` 当前只提供最新值与实时订阅，不是历史库。
- 协议页监视原始采集点时，应调用 `GetSourceLatest`，按协议连接的 `conn_id + tags` 获取源端最新值；该接口不依赖业务 Route，不应为了页面监视额外创建或持久化 Route。
- `GetSourceLatest` 的返回值只在 DataCenter 进程内缓存。页面应按 `ts_ms`、quality 和本地刷新结果区分正常、陈旧和不可用；DataCenter 重启后应显示“暂无数据”，等待协议模块下一次 Publish。
- 对于 IEC104 遥调/遥控进入 AGC/AVC 的控制链路，`Route` 仍然只表达点到点绑定；协议级接受或拒绝由 `DataCenter.ExecuteCommand` 同步转交目标模块后返回，不应在上位机或 IEC104 页面重复实现 AGC/AVC 容量校验规则。
- 上位机同步新版 `DataCenter.proto` 后，可以读取 `ExecuteCommandResponse.status/reject_code/reason/lower_limit/upper_limit` 辅助调试；正常主站控制仍通过 IEC104 协议下发，不要求上位机直接调用该 RPC。
- 若采用 `CONFIG_PUSHER` 严格目标态编排，路由涉及的源/目标连接都应在 `ConnTags` 中显式声明所需 tag；未声明连接的旧标签会被清空，不应再依赖历史残留。

## 5.5 控制策略

当前主要承载 `AGC`、`AVC` 与 `Calc`。

建议页面结构为：

- 控制组列表
- 控制组配置
- 成员配置
- 输入输出点说明
- 运行状态
- 控制日志

应重点展示：

- `group_name`
- `conn_id`
- `p_cmd`
- 成员量测点与设定点
- 分配策略
- 派生输出点
- 当前状态与最后错误

需要注意：

- 当前 AGC 不应继续展示旧版 `loop`、`kp`、`deadband_kw`、`max_step_kw` 等参数。
- 页面文案应强调“相关输入变化时直接按目标总功率分配”。
- AGC/AVC 控制组作为 IEC104 控制目标时，应展示同步命令拒绝原因；常见原因包括控制组未运行、目标点不匹配、缺少量测、总有功/总无功目标超过当前可调上下限。

### AGC/AVC 快速选点与自动路由

AGC/AVC 页面可从 DataCenter 已注册的连接与 tags 中快速选点回填控制组配置。该功能不是协议点表导入，上位机仍只向 AGC/AVC 保存模块内部 tag；外部 `module_name + conn_name + tag` 仅作为本次页面编辑的路由意图，不写入 AGC/AVC protobuf 配置。

- AGC `p_cmd` 保持手动填写，不提供从数据总线快速选点的入口。
- AGC 成员弹窗可为本次选择的 `p_meas`、`p_set`、`base_tag` 提供“保存控制组时自动创建 DataCenter 路由”复选框，默认不选中。
- AVC 组配置弹窗可为 `voltage_meas`、`voltage_cmd`、`q_total_cmd`、`q_total_cmd.base_tag` 提供同类复选框；成员弹窗则覆盖 `q_meas`、`q_set`、`base_tag`。
- 输入字段路由方向为“外部已选点 -> 当前控制组 tag”：AGC 的 `p_meas/base_tag`，AVC 的 `voltage_meas/voltage_cmd/q_total_cmd/base_tag/q_meas`。
- 成员设定输出的路由方向相反：AGC `p_set` 为“AGC 控制组 tag -> 外部已选点”，AVC `q_set` 为“AVC 控制组 tag -> 外部已选点”。
- 仅对用户确实通过数据总线下拉框选中、且复选框已开启的字段生成路由；手动输入的 tag 不猜测外部端点。
- 自动路由按 `replace=false` 增量提交，不删除 DataCenter 中已有的手工或历史路由；需要收敛旧绑定时应在数据总线页面明确删除。
- 不允许将当前 AGC/AVC 控制组连接本身作为自动路由的“外部点位”，避免产生自引用或回路。
- 创建路由时使用用户最终保存的控制组 tag，并仅下发稳定端点字段 `module_name + conn_name + tag`。
- 保存顺序必须是先调用 `AGC/AVC.UpsertGroup`，待模块将最终 tags 同步到 DataCenter `ConnTags` 后，再调用 `DataCenter.UpsertRoutes(replace=false)`。AGC/AVC 可能在 `UpsertGroup` 内部按现有语义自动启动控制组；上位机仍应紧接着提交路由，并按原运行态恢复流程处理后续启动结果。
- 若控制组已保存但路由创建失败，上位机必须明确提示部分成功，并保留已保存的控制组，不得回滚或误报为全部失败。

### Calc 页面建议

建议页面结构为：

- 计算分组列表
- item 列表与排序
- 运算符与左右操作数配置
- 内建点说明
- 运行状态
- 最近错误

应重点展示：

- `group_name`
- `conn_id`
- `item_name`
- `operator_kind`
- `left_input_tag`
- `right_input_tag`
- `result_tag`
- 当前状态与最后错误

需要注意：

- 上位机“选择已有点”应只负责帮助用户在 `数据总线` 中建立到 `left_input/right_input` 的 Route，不应让 `Calc` 再保存外部 `conn/tag`
- 数值运算只允许 `int64/double`，逻辑运算只允许 `bool`，不要在页面上做 bool 与数值的隐式互转
- `NOT` 仍保留统一的 3 个内建点展示；其中 `right_input` 只是不参与计算，不表示该点不存在
- item 作为 group 子配置统一随 `UpsertGroup` 覆盖提交，不建议为 item 设计独立的 CRUD RPC 假象

## 6. 推荐操作流程

## 6.1 首次建站或新增系统接入

推荐流程如下：

1. 先规划稳定的 `module_name + conn_name/group_name` 命名。
2. 在 `模块运维` 中启动 `DataCenter` 与目标模块。
3. 刷新运行信息，确认目标模块已进入运行态；若上位机内部需要直连模块接口，应根据 `GetRunningModuleInfo` 自动刷新连接信息，无需向用户展示或要求用户手工处理地址。
4. 在对应业务页中创建连接、控制组或计算分组，拿到稳定的 `conn_id`。
5. 在协议页下发点表，或在控制页下发控制组/计算分组配置；等待模块自动同步对应连接的 `ConnTags`。
6. 在 `数据总线` 中直接基于已出现的连接与 tags 配置 `Routes`。
7. 返回业务页；若对象需要启动模块内功能，则显式调用对应启动 RPC。对链路类对象，应调用 `StartLink` 启动模块内的链路连接功能，再结合 `state`、`last_error` 与日志确认是否进入运行态。
8. 进入业务页运行状态区与 `数据总线` 实时值监视区完成联调确认。

## 6.2 新增协议连接

推荐顺序如下：

1. 启动模块。
2. 新建连接。
3. 下发点表。
4. 进入 `数据总线` 页面，确认该连接的 tags 已自动出现后再配置路由。
5. 显式调用 `StartLink` 启动模块内的链路连接功能，再观察对象是否进入运行态；若未进入运行态，则结合 `state`、`last_error` 与日志修正配置后重新下发或重新启动。
6. 观察最新值、状态与日志。

不建议先启动连接再补点表或路由，否则容易出现“模块运行了但业务不通”的误判。

例如：

- 若 `ModbusRTU` 页面已配置 `A相电压/B相电压/C相电压` 三个点，`IEC104` 页面也已配置对应三个点；
- 则进入 `数据总线` 页面时，应直接看到这两个连接以及各自已同步出来的三相电压 tags；
- 用户此时只需要建立三条 `Route`：
  - `ModbusRTU.A相电压 -> IEC104.A相电压`
  - `ModbusRTU.B相电压 -> IEC104.B相电压`
  - `ModbusRTU.C相电压 -> IEC104.C相电压`
- 不应再要求用户在 `DataCenter` 页面重复录入第二份 `ConnTags` 或第二份点表。

`IEC104` 页面的“从现有点位添加”可以提供“同时创建 DataCenter 路由”复选框，用于将上述两步配置合并为一次用户操作。交互与执行语义如下：

- 复选框默认不选中；不选中时仅在当前 `IEC104` 连接中新增点表记录，保持现有行为。
- 选中时批量创建“来源点位 -> 当前 IEC104 点位”的单向 `Route`；目标 tag 使用用户在导入表格中最终确认的 tag。
- 路由端点应使用稳定字段 `module_name + conn_name + tag`；`conn_id` 只可作为当前运行态回填字段。
- 提交顺序必须是先下发 `IEC104` 点表、完成目标 tags 的 `ConnTags` 同步，再调用 `DataCenter.UpsertRoutes(replace=false)` 增量创建路由；运行中的链路应在两步完成后再恢复启动。
- 点表与路由属于两个独立接口，无法保证跨服务事务。若点表已成功而路由创建失败，上位机应明确提示“点表已保存，路由创建失败”，并保留点表，不得将整个操作误报为全部失败。
- 当当前 `IEC104.station_role=MASTER` 时，该方向的路由可能触发遥控或遥调命令，上位机必须给出明显警告；`SLAVE` 则表示将来源点值转为 IEC104 点值上送。
- 自动建路由不执行数据类型或工程量单位转换；来源值类型必须与目标 `IEC104` 点类型兼容，`scale/offset/deadband` 仍由目标点表配置解释。

## 6.3 新增 AGC 控制组

推荐顺序如下：

1. 启动 `DataCenter` 与 `AGC` 模块。
2. 创建控制组并获取 `conn_id`。
3. 配置 `p_cmd`、成员量测点、成员设定点与派生输出点。
4. 在 `数据总线` 配置上游输入路由与下游输出路由。
5. 若该控制组承接 IEC104 遥调，应配置 `IEC104.<总有功命令点> -> AGC.<p_cmd>` 的唯一路由；总量超过当前可调上下限时，AGC 会通过同步命令结果触发 IEC104 负确认。
6. 观察控制组是否自动进入运行态；若未进入运行态，则结合 `last_error` 与日志修正配置后重新下发。
7. 观察 `p_total_meas`、`p_total_target`、成员设定输出与日志。

## 6.4 新增 Calc 计算分组

推荐顺序如下：

1. 启动 `DataCenter` 与 `Calc` 模块。
2. 创建计算分组并获取 `conn_id`。
3. 在分组内一次性配置 items、运算符、常量与输入槽位来源。
4. 在 `数据总线` 中把已有点路由到 `<item_name>/left_input` 或 `<item_name>/right_input`。
5. 观察分组是否自动进入运行态；若未进入运行态，则结合 `last_error` 与日志修正配置后重新下发。
6. 在 `数据总线` 中观察 `<item_name>/result` 的最新值与实时更新。

## 6.5 日常运行

日常运行建议以以下页面为主：

- `总览`
- `数据总线` 的实时值监视
- 各业务页的运行状态摘要

原则上，运行期用户应尽量少进入配置编辑页面，减少误操作风险。

## 6.6 故障处置

建议按层次定位问题：

### 模块层

若模块不可达或接口连接失败：

- 返回 `模块运维`
- 刷新 `GetRunningModuleInfo`
- 确认运行信息已刷新
- 必要时重新启动模块

### 连接层

若连接未进入运行态：

- 查看 `state`
- 查看 `last_error`
- 若对象仍在运行态且需要修改配置，先停止对象功能
- 修正连接参数、点表或 MQTT 等前置配置
- 重新下发配置；若需要再次启动模块内的链路连接功能，再显式调用 `StartLink`

### 数据层

若模块已运行但数据不通：

- 检查 `conn_id` 是否匹配
- 检查 `ConnTags` 是否存在且正确
- 检查 `Route` 是否配置完整
- 检查源 tag 与目标 tag 是否一致或按预期重写

### 删除失败

若对象删除后进入 `PENDING_DELETE`：

- 先确认 `DataCenter` 是否可达
- 恢复后重试删除
- 必要时重新建立对象并重新梳理路由

## 7. 关键交互约束

上位机在设计时必须强调以下约束：

- “启动模块”应作为模块级正常主路径动作，与后续“启动模块内功能”分开设计。
- “启动模块”和“启动模块内的连接功能/控制组功能”应分开表达；对于 IEC104、ModbusRTU、DLT645 等协议连接，`StartLink` 应作为显式启动模块内链路连接功能的正常入口；对于 AGC/Calc 等分组对象，也应保留对 `StartGroup`/`StopGroup` 语义的清晰表达。
- `conn_id` 应展示为关键只读字段。
- 协议点表编辑页与 `DataCenter` 标签注册页必须分开。
- 对于已自动同步 `ConnTags` 的连接，`DataCenter` 页面应默认复用业务页已生成的 tags 做路由配置，不应要求用户重复手工维护第二份 tags。
- 修改运行中对象前，应先停止连接功能或控制组功能。
- 对删除操作应给出二次确认，尤其是涉及 `DeleteConnection`、`DeleteLink`、`DeleteGroup` 时。
- 对 `replace=true` 类操作应做显式提醒，避免用户误覆盖既有配置。

## 8. 两种接入模式建议

## 8.1 上位机直控模式

适用于在线维护、单点调试、增量调整。

推荐顺序：

1. 启动模块
2. 创建连接、控制组或计算分组
3. 下发点表、控制配置或计算配置
4. 配置 `DataCenter` 路由
5. 若对象是协议连接，则显式调用 `StartLink` 启动模块内的链路连接功能；若对象是控制组或计算分组，则按对应模块语义确认其是否进入运行态。未进入运行态时查看 `state`、`last_error` 与日志并修正配置

## 8.2 ConfigPusher 初始化模式

适用于批量初始化、预制配置下发、现场快速部署。

需要注意：

- `ConfigPusher` 当前更偏向配置编排执行器。
- 它不适合作为上位机统一的日常在线操作入口。
- `ConfigPusherService` 当前只有 `Ping`，没有远程触发配置下发的对外 RPC；默认是模块在启动且 `boot_config_mode=CONFIG_PUSHER` 时读取本地 `jsonc` 执行编排。
- 上位机在该模式下更适合作为配置生成、校验、导入与状态观察工具。
- 在 `CONFIG_PUSHER` 模式下，上位机生成的 `jsonc` 应视为目标态快照，而不是增量补丁；未出现在 `jsonc` 中的旧链路、旧控制组、旧点表、旧连接标签注册表与旧路由，会在下次编排时被收敛删除或覆盖。
- 上位机在该模式下不应依赖“保留旧持久化局部配置”的隐式行为；若希望对象继续存在，应显式保留在本次 `jsonc` 中。
- `start` 字段在 `ConfigPusher` 模式下仅保留兼容日志意义，不应被上位机设计为“必须点击后才会生效”的主路径操作。

### 建议同步记录的能力清单

如果后续要让上位机配合 `ConfigPusher` 工作，建议单独维护并优先参考专门的能力矩阵文档：

- [`doc/ConfigPusher能力矩阵.md`](./ConfigPusher能力矩阵.md)

该文档应作为以下内容的统一锚点：

- `IEC104/ModbusRTU/DLT645/AGC/DataCenter` 各类模板对象的能力边界。
- 目标态覆盖、旧对象收敛删除、配置类 RPC 不自动启动模块内功能等公共语义。
- 实际调用的模块 RPC、前置依赖、常见失败条件与补救路径。

导入结果页建议同时体现以下执行语义：

- 当前编排是串行执行，不是事务型批处理。
- 允许部分成功，不应只返回一个笼统的“导入成功/失败”。
- 失败后默认依赖日志、对象状态和对应模块页面做补救，而不是假设 `ConfigPusher` 存在黑盒回滚或自动重试。

### 页面与职责边界

上位机如果同时支持“初始化导入”和“在线维护”，建议明确拆成两类页面：

- `模板导入/批量初始化` 页面：面向 `ConfigPusher` 模型，负责生成 `jsonc`、校验目标态、展示导入预览与差异。
- `协议与控制在线维护` 页面：面向各模块原生 gRPC 模型，负责单连接、单控制组、单点表的在线增量修改。
- `数据总线` 页面：面向 `DataCenter` 路由与实时值，不把 `ConfigPusher` 的模板字段直接暴露成运行期主编辑入口。

不建议把 `ConfigPusher` 表单直接当成上位机唯一配置页，否则会混淆两类动作：

- “批量导入后按目标态收敛”
- “对单个运行中对象做在线增量维护”

### 推荐最小交付物

如果要开始和上位机同步，建议优先形成以下产物：

1. 一份按对象分类的 `ConfigPusher` 能力矩阵。
2. 一份模板字段约束与示例清单，覆盖 `IEC104/ModbusRTU/DLT645/AGC/DataCenter`。
3. 一份“模板模型 -> 模块原生 RPC 模型”的映射说明，避免前后端、联调人员对同名字段产生不同理解。
4. 一份导入预检规则，至少覆盖必填项、依赖模块、批量展开结果、目标态覆盖风险与删除影响提示。

## 9. 后续扩展建议

如果后续继续完善上位机，建议优先补齐以下能力：

- 原型级页面草图
- 页面到 gRPC 调用的映射表
- 角色权限划分
- 历史数据或趋势系统对接方案
- 协议模板/草稿库：支持按协议保存当前控制面配置、从模板新建、加载后修改再保存；模板不包含 `conn_id`、运行状态、运行地址、日志等运行态信息。
