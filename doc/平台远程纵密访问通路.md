# 平台远程纵密访问通路

## 已确认目标（2026-10-29）

用户已确认开始实现：在上位机“纵密 / 访问通路”选择平台 DSP，通过平台远程配置该 DSP 的纵密维护访问通路，并检测“上位机 → 平台 → DSP → 纵密装置”是否连通。访问能力仅供上位机内部使用；纵密账号认证仍属于独立登录页面，本轮不扩展远程登录业务。

## 实现边界与接口

- 配置复用既有固定 101/108 维护脚本和独立开机恢复服务，不改变纵密业务网络、PPP、默认路由或配置来源。配置与检测由用户分别点击执行，不自动登录装置。
- 配置请求在既有上传账号、SSH 认证、sudo 密码之外增加可选 `device_id`。远程模式仅使用所选设备的 SSH 服务，账号地址由后端替换为内部隧道；不得回退直连或改用全局所选设备。密码仅供当前操作使用。
- 检测请求继续使用 `{mode, device_id?}`。远程检测先核验当前平台授权与在线状态，再通过固定服务 `vertical-security` 探测 `11.22.33.44:8888`，最后验证现有配套证书的 TLS 握手；不发送纵密账号。
- 下位机仅在已有平台 SSH 维护能力启用时登记 `vertical-security`；该服务固定目标和端口，不接受上位机任意 IP/端口。普通模块仍只允许连接环回地址。
- 平台将 `vertical-security` 归入已有 SSH 维护权限，与 `ssh` 一样受 `allow_ssh` 控制；仅有 `allow_grpc` 不允许使用纵密维护通道。沿用现有账号、设备、票据、撤权和流量限制机制，不引入协议字段或数据库迁移。
- 配置复用既有远程 SSH 主机指纹信任机制；未信任或指纹变化时拒绝执行并说明须先在远程终端确认设备身份。配置支持 SSH 密码认证；直连原有证书认证保留。
- 远程配置失败、超时或中断保留分阶段结果，不能宣称撤销已执行的网络变更。成功配置只表示脚本应用完成，须再次检测确认纵密可达。
- 检测为有界只读探测，结束释放内部转发资源，不安装虚拟网卡、不修改电脑路由、不向外部软件提供 IP 网络。没有持久网络会话，`session_id` 仍为 null；界面称“检查通过”，不得声称整个网络或所有端口可用。
- 配置和检测锁定当前模式及 DSP；切换目标、平台会话变化、卸载页面后旧结果不得覆盖新目标。不影响其他业务页面的全局 DSP 选择。
- 页面展示平台设备、远程管理通道、纵密管理端口和 TLS 的实际阶段。平台在线、SSH 可达不单独判定纵密可达。更新“端口不限”等与内部管理服务不符的文案。

## 验收与测试顺序

先补针对原未支持行为的失败测试，再实现：下位机固定服务登记、目标解析和普通模块环回限制；平台仅 SSH 授权放行纵密服务、列表过滤与撤权；上位机远程配置严格绑定设备、认证与未知结果处理，远程检测真实隧道与 TLS 探测；页面远程配置入口、请求绑定、锁定与旧结果保护。

本机执行可用的相关单元、契约、浏览器交互、类型检查和构建检查。下位机无本机完整编译工具链时明确未编译部分，不为此安装工具链。设备部署、远端编译和真机联调尚未授权，本轮不执行；本地通过不等于现场通路已验证。
