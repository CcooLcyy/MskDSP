# 下位机 gzip 安装包方案

## 已确认的目标与边界

下位机统一发布 gzip 压缩载荷，不兼容旧的未压缩安装包。安装文件保留可执行 Bash 脚本头、`__ARCHIVE_BELOW__` 分界标记和 `start` 安装命令；标记之后必须是完整的 gzip 镜像 tar。上位机下载、缓存和上传均保持原始压缩字节，到下位机由 Docker 加载。用户已确认按此方案实施。

本次不改变业务镜像内容、配置来源、容器切换策略和更新通道，不增加镜像层增量或自动回滚，也不发布正式版本或访问设备。

## 发布与安装

- 发布脚本只接受不超过 4 GiB 的未压缩原始镜像 tar，拒绝已压缩输入，避免产生双重压缩包；在封装时以 gzip 级别 6 压缩，关闭压缩文件名和时间戳记录。对最终可执行包生成大小和 SHA256，镜像 config 摘要保持不变；封装失败清理不完整输出。
- 安装脚本提取压缩载荷至临时文件，明确拒绝裸 tar、损坏或截断的 gzip；校验镜像清单、平台关联和 config 摘要后，交给 `docker load` 直接解压加载，不落盘完整未压缩 tar。
- gzip 完整性检查和镜像身份校验在替换业务容器之前完成；载荷提取、校验或加载失败时清理临时文件，不进入容器切换。
- 保留下载失败、上传失败和镜像加载失败的现有处理，新增中文压缩格式日志与可操作的错误提示。

## 上位机接口与缓存

- 资产清单格式保持现有 schema，`asset.size` 与 `asset.sha256` 必须指向最终压缩自解压包。
- 本地导入仅接受脚本头后的单成员 gzip 载荷，最大解压总长度为 4 GiB，完整检查 CRC、截断与尾随数据，使用有界的流式解压读取 tar 元数据，不把整个镜像解压到内存；保留重复路径、路径格式、元数据大小、平台和摘要关联检查。下位机安装器采用相同的单成员与总量约束。
- 本地导入、在线下载缓存恢复和上传前均校验 gzip 载荷格式，旧裸 tar 包提示重新下载；在线文件字节不做解压或重写。
- 缓存格式版本升级，首次启动自动清理旧格式元数据对应的包及无元数据旧包；保留当前格式有效缓存，清理限于下位机更新缓存目录。
- 发布顺序建议先交付新上位机，再发布压缩下位机包。旧上位机的本地导入不支持新格式。

## 验收与验证

1. 发布产物的 gzip 解压字节与输入镜像 tar 完全相同，镜像 config 摘要不变，最终包可执行且清单大小与 SHA256 正确。
2. 下位机首次安装、同镜像跳过加载、真实更新和加载失败分支仍通过隔离 Docker 模拟测试；裸 tar、gzip CRC 错误与截断包在容器替换前失败。
3. 上位机支持 gzip 中 Docker/OCI 两种镜像归档布局与 ARM64/x64 平台，拒绝旧载荷、损坏压缩、重复路径和非法元数据。
4. 旧缓存清理、新缓存保留及下载/上传字节透传有回归验证。
5. 本机执行可用的 Python/Bash 脚本测试、Rust 测试及前端检查；真机 gzip 解压耗时、内存、磁盘与真实 `docker load` 验证在另行确认设备范围后进行。此前三个发布包压缩实验约节省 70% 传输量，不作为真机升级耗时承诺。
