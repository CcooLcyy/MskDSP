# Linux CI 共享内存工作区

## 目标与范围

两个 Linux Docker Runner 共用一个容量上限为 24 GiB 的临时文件系统，减少编译中间文件、临时文件和产物交接对系统盘的读写。Windows Runner、业务容器、持久依赖缓存与 BuildKit 的持久状态不迁移。

24 GiB 仅限制共享文件容量，不是所有编译进程的总内存限额，也不预先分配物理内存。重编译阶段通过共享的两个编译槽控制并发，下位机 Runner 接单并发为 2，通用 Linux Runner 为 1，主工程默认 4 路编译。

## 输入、隔离与生命周期

- 使用 Docker local 驱动创建命名卷 `mskdsp-ci-ram`，参数为 `type=tmpfs`、`device=tmpfs`、`o=size=24g,noswap,mode=1777`。Docker 守护进程负责挂载，无需额外修改宿主机 fstab 或启动特权容器。
- 两个 Runner 都把同一个卷挂到实际作业容器、helper 和作业级保持服务的 `/builds`；管理容器本身无需挂载。下位机检出路径为 `/builds/lower/$CI_PROJECT_PATH/$CI_PIPELINE_ID/$ARCH`，通用 Linux Runner 为 `/builds/linux/$CI_PROJECT_PATH`。同一流水线的同一架构按依赖关系顺序执行，编译与独立测试的路径保持一致；不同流水线和架构的目录隔离。通用 Runner 仍只允许一个作业。
- 每个作业增加 `ci-ram-lease` 服务，使用本地已有 `alpine:3.20` 执行 sleep；单服务上限 64 MiB、0.1 CPU、禁止交换。服务不监听端口，两个专用 Runner 禁用服务端口健康等待。配置工具拒绝带其他服务的配置，避免影响已有数据库等服务。
- 保持服务在源码准备之前运行，直到归档和清理结束后才移除。必须保留：Docker local tmpfs 会在最后运行容器停止时卸载，仅创建一个空命名卷不能保证 helper → 编译容器 → helper 之间的数据连续性。
- 下位机 build/test 作业必须保留相同的工程绝对路径，继续验证构建身份与 `build_context.json`，完整 x64 CTest 门禁不变。
- 作业使用 `GIT_STRATEGY=clone` 和 `FF_ENABLE_JOB_CLEANUP=true`。归档上传后由 Runner 清理当前工程目录；不得在 after_script 中提前删除产物。
- 最后一个作业的保持服务释放挂载后，tmpfs 自动卸载、全部文件释放。已通过双容器小容量探针验证共享可见性、使用期间保留以及最后消费者释放后内容消失；另验证停止容器即可能卸载，阶段交接验收必须包含保持服务。
- 仍在运行或被保留的异常作业容器会继续持有卷；不通过按目录年龄删除的方式猜测其是否安全。停止并清理对应异常容器后可自动回收，诊断工具需要报告这些消费者。

## 作业准备与资源边界

公共准备脚本检查工作区文件系统为 tmpfs、剩余空间和作业目录边界，创建工程内的临时目录并设置 TMPDIR/GOTMPDIR。每个编译槽贯穿本次作业的主脚本执行，覆盖 buildctl 请求的远端编译，全局最多同时运行两个主脚本；第三个作业等待可用槽。归档与源码准备仍可能重叠，需监测峰值。

公共脚本同时用于 Debian 工具镜像和 BusyBox BuildKit 镜像，目录解析不得依赖 GNU `realpath -e`。使用子 shell 中的 `CDPATH= cd "$CI_PROJECT_DIR" && pwd -P` 解析已存在目录的物理路径，目录不存在或无法进入时立即失败；保留解析前后的路径边界、tmpfs、容量与编译槽检查。回归须在两类镜像中覆盖正常目录、含空格目录、允许范围内的符号链接、不存在目录及符号链接越界，并验证不改变主作业当前目录。

现有 ccache、vcpkg 源码/下载/二进制缓存、Cargo target/CARGO_HOME、Go 编译缓存继续持久保存。BuildKit 内部缓存不属于 Runner 的工作区，保留其磁盘缓存以免每轮全量重编；内存工作区不等于消除全部磁盘写入。

内存盘消耗计入实际写入容器的内存核算，作业内存与编译进程共用限额。配置明确禁止构建容器交换，使用空间/内存诊断和有界并发防止退化为交换 I/O。内存或空间不足时明确失败，不静默回退系统盘。

## 异常、部署与回退

部署工具校验现有 Runner 配置并备份，只修改两个指定 Linux Runner；不打印 URL、token 或完整配置。等待当前作业结束后热加载配置；不终止已运行的构建。卷配置不匹配时拒绝覆盖。回退恢复备份配置即可，新作业重新使用磁盘工作区；有活跃消费者时不删除卷。

## 验收

1. 单元测试覆盖卷配置、配置更新的保密与幂等、目录边界、共享锁、资源限制与回退。
2. 两个容器看到相同文件，容量合计为 24 GiB，挂载含 noswap；保持服务覆盖源码准备、编译与归档容器的切换，最后消费者退出后实际内存文件释放。
3. 实际 Runner 作业校验工作区、跨 Runner 隔离、归档 helper 可见性与任务成功/失败后的清理。
4. 运行下位机 build → artifact → 独立 x64 CTest 验证，记录内存、空间、CPU I/O 等待与产物状态；不绕过原测试或发布门禁。

## 编译缓存跨目录复用

RelWithDebInfo 的调试信息会把工作目录纳入 ccache 缓存键。仅设置 CCACHE_BASEDIR 不足以跨流水线目录复用，C/C++ 编译参数同时添加 -fdebug-prefix-map 和 -ffile-prefix-map，将工程路径映射为 /usr/src/mskdsp；不关闭 hash_dir 或放松文件校验。实际工具镜像 ccache 4.9.1 / GCC14 的最小真实编译验证：未映射时两次跨目录编译均未命中，映射后第二次直接命中且两份对象字节相同。

持久 ccache 默认上限调整为每架构 8G（ccache 配置值），可通过 CCACHE_MAXSIZE 配置；不占共享内存卷配额。首次启用新参数需要建立新缓存，后续流水线分别记录命中率，不能将冷缓存首轮当作温缓存提速结论。

## 发布交接与独立调试符号

2026-10-24 的暖缓存流水线 157 中，ARM64 打包归档约 183 MB，其中独立符号约 132 MB、实际安装包约 50 MB；x64 打包归档约 194 MB，几乎全部是包含调试信息的安装包。两架构发布程序只消费安装包及其冻结元数据，发布准备阶段却仍各花约 73 秒下载整个归档。

本轮优化范围及契约：

- ARM64、x64 均启用既有符号分离流程，生产二进制保留 GNU debuglink，测试可执行文件继续保留调试信息。x64 必须在分离符号后的生产库上通过完整 CTest，不修改测试集合或原构建身份校验。
- 构建作业在 `symbols/$ARCH/` 下生成独立符号压缩包、SHA256SUMS 和原始构建身份，符号必须非空且校验失败时阻断构建。两种架构的构建归档均保留 30 天，排除原始 `package/debug/**`，避免再归档一份未压缩符号。该选择会延长构建归档内运行文件和测试依赖的保留时间，换取无需新增重复下载作业即可保留符号。
- x64 测试交接不再上传符号或原始 debug 目录；打包不依赖调试符号。安装包与独立符号可通过相同的原始构建身份关联，符号始终可从构建作业归档单独下载。
- 打包归档只保留安装包、冻结 metadata.json、安装包 SHA256SUMS 及本次 package.log；不再传递符号、旧构建/测试日志和中间身份文件。打包失败的诊断仍由 package.log 和完整作业日志提供。
- 仅发布作业采用 `GIT_DEPTH=1`；构建的完整历史及 vcpkg 基线校验不变。发布保留远端主分支 HEAD、流水线/提交身份、安装包大小/SHA256、发布结果和清单核对。
- 两架构均打包成功后才能发布的依赖关系、独立 x64 测试门禁、资源锁及工作区回收保持不变，不合并打包与发布阶段。

验收先运行编排与 CI 契约测试，再提交推送触发真实双架构流水线。记录安装包及符号大小、产物下载阶段耗时、完整 CTest、缓存命中和总耗时；首次参数变化若造成缓存重建，应再测同提交暖轮，不能预先承诺耗时降幅。

已用现有 x64 CI 工具镜像的 GCC14 编译最小真实共享库和测试程序，调用仓库的 strip_debug.sh 验证：生产库分离后可执行、测试程序 SHA256 不变、生产库不再含 debug_info、独立符号仍含 debug_info，GNU debuglink 中 CRC 与独立符号文件匹配。该探针验证真实 ELF 处理，不代替产品完整 CTest。
