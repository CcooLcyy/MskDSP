# IEC104 启动阶段重载配置自锁死锁修复方案

## 1. 现象

上位机（MskDSP Upper）打开「协议接入 → IEC104」页面后一直转圈，连接列表始终为空，
手动点「刷新」也没有任何反应；同一时刻 ModbusRTU / ModbusTCP / DLT645 / IEC61850 页面全部正常。

下位机侧表现更隐蔽：

- MskDSP 进程存活、CPU 占用接近 0、线程数正常，模块列表里 IEC104 也在「运行中」；
- IEC104 模块日志在模块启动那一刻（例如 `09:24:52`）**写完最后一行后彻底静默**，之后不再产生任何日志；
- 对 IEC104 对外 gRPC 端口（示例 `17796`）发起**全新连接**调用只读接口 `ListLinks`，
  在超时时间内**没有任何响应**；对同机其它模块端口发起同样调用则立刻返回。

即：IEC104 模块在启动阶段把自己锁死了，其 gRPC 服务从此永久不可用，且不会自愈，只有重启进程才能恢复。

## 2. 影响范围

- 只要 IEC104 发生过一次该死锁，该模块的**全部** gRPC 接口（`ListLinks` / `GetLink` /
  `GetPointTable` / `UpsertLink` / `StartLink` / `StopLink` / `QuerySoe` / 模拟值接口…）全部永久阻塞。
- 上位机侧表现为页面无限转圈；重连、切页、点刷新都无法恢复，必须重启下位机进程。
- 上位机自身的实时数据链路（DataCenter gRPC）不受影响，因此现象看起来是「只有 104 卡住」。

## 3. 根因

`LinkManager` 只有一把非递归互斥量 `mu_`，全部运行态都受它保护
（`src/IEC104/include/IEC104LinkManager.h`）。死锁是**同一线程重入 `mu_`** 造成的，链条如下：

1. `IEC104` 模块对象构造时，`LinkManager` 构造函数调用 `loadPersistedConfig("构造阶段")`
   （`src/IEC104/IEC104LinkManager.cc`），恢复持久化链路并在末尾执行
   `TryAutoStartReadyLinks(trigger)`；此时链路被真正启动：`StartLink` → `TcpLink::Start()`
   拉起传输线程并注册连接状态回调。
2. `IEC104::start()` 在 gRPC 服务构建完成后调用 `linkManager_.LoadPersistedConfig()`
   （`src/IEC104/IEC104.cc`），触发 `loadPersistedConfig("模块启动阶段重试")` 再做一次整表重载。
3. 重载代码在**持锁**状态下就地替换链路表（修复前）：

   ```cpp
   {
     std::lock_guard<std::mutex> lock(mu_);
     linksByName_ = std::move(restoredLinks);   // 就地析构旧的 LinkRuntime
     ...
   }
   ```

   旧 `LinkRuntime` 的析构会依次销毁订阅线程与 `TcpLink`。
4. `~TcpLink()` → `TcpLink::Stop()` → `setConnectionState(CONNECTION_STATE_DISCONNECTED)`
   （`src/IEC104/IEC104TcpLink.cc`），该方法在打完日志后**同步回调**已注册的连接状态回调。
5. 该回调是 `LinkManager::handleTransportConnectionState`，它第一件事就是 `mu_.lock()`
   （`src/IEC104/IEC104LinkManager.cc`）。线程已持有 `mu_` 且 `std::mutex` 不可重入，
   于是**永久阻塞**，`mu_` 再也不释放。

关键观测点：死锁前最后一条日志恰好是 `TcpLink::setConnectionState` 打出的
「IEC104 TCP 链路连接状态变化: … 状态=已断开」，而紧随其后的
「IEC104 本地持久化配置加载完成」与「IEC104 自动启动检查完成…」永远不会出现。

### 触发条件（为什么是「经常」而不是「每次」）

同时满足以下两条即必然死锁：

1. 持久化中存在**至少一条有效链路且其点表非空**（`checkStartPreconditionsLocked` 才放行自动启动）；
2. 该链路在 `IEC104::start()` 的重载之前就已被自动启动，并且析构时 `TcpLink` 的内部状态
   **不是** `CONNECTION_STATE_DISCONNECTED`（例如客户端链路处于「连接中」）。

现场点表落盘并自动启动后，冷启动大多满足这两条；早期尚未落盘点表的启动则不会触发，
所以表现为「经常卡」而非「每次卡」。

### 同类隐患

同一把锁的保护范围内还做过多处线程 `join()`：

- `loadPersistedConfig` 持锁替换链路表 → 同时析构三个订阅 `std::jthread`（析构即 join）；
- `StopLink` 持锁调用 `stopDataCenterSubscribeLocked` / `stopTimeSyncSubscribeLocked` /
  `stopCommandSubscribeLocked`，内部 `request_stop() + join()`。

而订阅线程的运行期回调（`isSimulationValueActive`、异常结束时的 `lastError` 回写等）同样要获取
`mu_`。一旦被 join 的线程此刻正卡在等待 `mu_` 上，同样会永久死锁。属于同一类缺陷，一并修复。

## 4. 修复方案

### 4.1 旧链路在锁外回收（根因）

`loadPersistedConfig` 中先把旧的 `linksByName_` / `reservedServerListenByName_`
用 `swap` 摘出到局部变量（`swap` 保证锁内不发生任何链路析构），装上新的链路表并释放锁之后，
再让旧链路 `clear()` 析构；同时补充中文日志记录被替换的链路数与监听端点数，便于后续定位。

### 4.2 析构前摘除传输层回调（防御）

新增匿名命名空间函数 `detachTransportCallbacks(TcpLink*)`，清空 `TcpLink` 的全部业务回调
（连接状态、点值、总召唤快照、SOE 重放/确认、对时、命令、命令执行模式）。
两处调用：

- `LinkRuntime` 的显式析构：销毁 `transport` 之前先摘除回调，无论链路在何处被销毁都不会反向回调
  `LinkManager`，不再依赖「新链路 `connectionState` 恰好等于 DISCONNECTED」这种隐式巧合；
- `StartLink` 替换 `link.transport` 之前：该处持锁，属于同一类点位，一并摘除。

`LinkRuntime` 因此必须显式声明默认构造、析构与移动语义（含一个 `std::jthread`，
不能退化为拷贝）。

### 4.3 订阅线程的 join 移出锁

新增 `SubscribeShutdown`：一个只负责「持有时承载待停止的订阅线程与 `ClientContext`，
析构时执行 `request_stop() + join()`」的小对象。它在**获取 `mu_` 之前**声明，
因此析构（真正 join）发生在锁已释放之后。

`StopLink` 与 `StartLink` 改为：在锁内只把订阅线程「摘出」到 `SubscribeShutdown`，
锁外完成停止与回收。三个 `stopXxxSubscribeLocked` 相应改为 `detachXxxSubscribeLocked`，
停止日志带上 `conn_name` 与订阅类型。

同时把旧 `transport` 一并摘出到局部 `std::unique_ptr`，靠局部对象「后声明先析构」的顺序保证：
先 `join` 订阅线程，再销毁 `transport`（订阅线程以裸指针引用 transport，不能先于它释放）。

## 5. 测试与验收

回归用例：`test/iec104_persistence_test.cc`
→ `IEC104PersistenceTest.ReloadAfterAutoStartKeepsManagerResponsive`

用例先落盘一条客户端链路（指向用例内起的本地监听端口）与非空点表，再新建 `LinkManager`
并注入 DataCenter Stub 触发恢复与自动启动，然后**等待传输层真正进入「已连接」**
（死锁触发点要求旧传输层状态不是「已断开」），最后调用 `LoadPersistedConfig()`
模拟模块启动阶段重载，断言重载与随后的 `ListLinks` 都能在看门狗超时内返回。
用例按 AGENTS 约定「先补可复现的失败测试」，修复前必然死锁、修复后通过。

死锁无法回收，因此看门狗检测到超时会打印中文失败信息并直接以失败码退出测试进程，
避免测试自身被永久挂起、把整个 ctest 任务拖死。

验收标准：

- 新增用例在修复前失败（死锁），修复后通过；
- `iec104Persistence_test`、`iec104LinkManager_test`、`iec104GrpcService_test`、
  `iec104TcpLink_test` 全量通过；
- 现网复现验证：冷启动后 IEC104 模块日志在启动阶段之后继续输出，
  上位机 IEC104 页面连接列表正常加载。

## 6. 本次未覆盖

上位机 `MskDSPUpper` 侧的两处放大效应**不在本次范围**，单独排期：

- `src-tauri/src/grpc/connection.rs` 的 `Channel` 无 `connect_timeout` / 请求 `timeout` /
  keepalive，失败通道也不从缓存剔除；
- `src/pages/IEC104/index.tsx` 的 `refreshLinks` 用未决 Promise 做并发去重，
  首个请求不返回会导致后续轮询全部空转，界面永久转圈。

下位机修复后本故障不再触发，但连接半开（下位机断电/拔网线时请求正在飞行）仍会命中上述两点。

## 7. 风险与回滚

- 改动集中在 `src/IEC104`，不涉及协议语义、点表格式与 gRPC 接口定义，无兼容性影响。
- 4.1 只改变旧链路的析构时机（锁外），链路表内容与顺序不变。
- 4.2 只在析构路径摘除回调，不影响链路运行期行为。
- 4.3 只改变订阅线程停止的执行位置与顺序（先停传输、后 join 订阅）；订阅线程发送前均会判空，
  传输已停止时发送被安全丢弃。
- 回滚：还原 `src/IEC104/include/IEC104LinkManager.h`、`src/IEC104/IEC104LinkManager.cc`、
  `src/IEC104/IEC104LinkManagerDataCenter.cc` 与新增测试用例，并删除本方案文档即可。
