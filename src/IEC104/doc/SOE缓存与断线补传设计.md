# IEC104 SOE 缓存与断线补传设计

## 1. 目标与范围

本文中的“每个通道”按每条 IEC104 连接（`conn_name`）理解。每条连接独立保存最近 8000 条遥信 SOE 历史，连接之间的容量、事件序号和确认状态互不影响。

本功能只处理从站向主站自发上送的单点遥信事件：

- DataCenter 到达一个单点遥信事件后，必须先写入 SQLite，再尝试通过 IEC104 上送；
- 每条记录包含本地事件序号、连接名、IOA、分合状态、毫秒时标、IEC104 品质和确认状态；
- SOE 使用带 CP56Time2a 时标的 `M_SP_TB_1`，原因码使用自发 `COT=3`；
- 通信恢复后，按本地事件序号升序补传所有未确认事件；
- 已收到对端传输层确认的事件仍作为历史保留，但不再补传；
- 设备重启或掉电后，事件内容和确认状态均从 SQLite 恢复。

遥测、总召快照、遥控响应、对时等普通 IEC104 报文不进入 SOE 历史。

## 2. 容量与覆盖规则

每条连接的有效容量固定为 8000 条。插入新事件后若该连接超过容量，在同一事务中删除事件序号最小的记录，直至记录数回到 8000。

覆盖规则不区分已确认和未确认记录，始终覆盖最旧记录。若被覆盖记录中包含未确认事件，记录告警日志，日志至少包含连接名、被覆盖数量和未确认数量。不同连接的事件不得被连带删除。

## 3. 持久化模型

SQLite 表按 `(conn_name, event_seq)` 唯一标识事件。`event_seq` 在每条连接内单调递增，不因覆盖、确认、进程重启或链路停止而回退。连接改名时，同一事务迁移事件和序号进度；链路最终删除成功后，删除该连接的 SOE 历史和序号进度。

建议字段如下：

| 字段 | 含义 |
| --- | --- |
| `conn_name` | IEC104 连接名 |
| `event_seq` | 连接内本地事件序号 |
| `ioa` | 信息对象地址 |
| `state` | 遥信状态，0 为分、1 为合 |
| `ts_ms` | 事件毫秒时标 |
| `quality` | IEC104 单点品质字节 |
| `acknowledged` | 是否已被 IEC104 传输层累计确认 |

本地事件序号用于持久化、排序及当前会话的确认关联，不写入标准 IEC104 单点信息体。主站收到的仍是标准 `M_SP_TB_1` 报文。

## 4. 发送与确认

SOE 不进入普通点值的合包和按 IOA 去重队列。每条 SOE 独立生成一个 I 帧，以保持事件顺序，并建立以下仅在当前 TCP 会话有效的映射：

```text
本地 event_seq -> 承载事件的 I 帧 N(S)
```

I 帧和 S 帧都可能携带接收序号 `N(R)`。`N(R)` 是累计确认号，表示对端已经正确接收序号小于 `N(R)` 的所有 I 帧。会话处理有效 `N(R)` 时，按发送顺序移除已确认 I 帧，并将这些帧关联的 SOE 批量标记为已确认。

`N(S)` 在新 TCP 会话中从零开始，不能作为持久化事件主键，也不持久化帧映射。发生断线、进程退出或掉电时，只有已经处理过有效 `N(R)` 的事件保持“已确认”；其余事件在新会话激活后重新查询并补传。

标准 IEC104 在连接中断时无法判定最后一个未确认 I 帧是否已被主站业务侧处理，因此本方案提供的是至少一次交付语义：

- 已确认事件不会再次补传；
- 已发送但未确认事件可能在重连后再次到达主站；
- 不允许仅因本地 socket 写成功就标记事件已确认。

## 5. 会话恢复顺序

新 TCP 会话完成 `STARTDT`、数据传输进入激活状态后，只执行一次 SOE 恢复：

1. 从 SQLite 查询该连接全部未确认事件；
2. 按 `event_seq` 升序生成 `M_SP_TB_1`；
3. 受 APCI `k` 发送窗口约束依次发送；
4. 同一时刻新落盘的实时事件排在已经取得的历史事件之后；
5. 收到有效 `N(R)` 后批量更新确认状态，并继续排空发送队列。

同一 TCP 会话内重复收到 `STARTDT` 不得重复装载历史。创建新会话后才重新查询仍未确认的事件。

## 6. 异常处理

- SQLite 初始化、插入或查询失败：记录错误日志，不发送未成功落盘的实时 SOE；
- 确认更新失败：记录错误日志，事件保持未确认，后续重连允许再次补传；
- 非法或越界 `N(R)`：沿用现有 IEC104 会话错误处理，关闭连接，不更新 SOE 确认状态；
- SOE 时标无效：ASDU 构造失败时记录告警，事件继续保留为未确认；
- 最旧未确认事件因容量限制被覆盖：记录溢出告警，后续无法再补传该事件。

## 7. 验收标准

- 单条连接写入 8000 条后全部可查询；第 8001 条写入后仅最旧一条被覆盖；
- 两条连接分别拥有独立的 8000 条容量和独立事件序号；
- 事件按序号升序恢复，状态、IOA、时标和品质保持不变；
- 确认后事件仍在历史中，但不出现在未确认查询中；重建存储对象后确认状态不丢失；
- 链路改名后事件和序号进度迁移，链路删除后对应历史被清理；
- SOE 不受普通点值去重开关影响，并始终使用带时标单点报文；
- I 帧或 S 帧中的有效累计 `N(R)` 只确认其覆盖的 SOE；重复确认不重复回调，越界确认不确认任何 SOE；
- 新会话激活后按序补传未确认事件，已确认事件不补传。
